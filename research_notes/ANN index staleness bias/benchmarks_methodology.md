# How dynamic/streaming ANN search is benchmarked, and whether anything measures per-item, per-age or per-query recall

Research date: 2026-11-23. Labels: "preprint" means an arXiv paper with no peer-reviewed venue confirmed. "PR" means peer-reviewed (venue confirmed from a primary page).

## Q1. NeurIPS'23 Big-ANN streaming track: recall measurement, workloads, the recall bug, winners, follow-ups

### Takeaway
The streaming track reports **one number per runbook**: recall@10 averaged over all queries at all search checkpoints. Ground truth at each checkpoint is the set of points live at that moment. The final workload is k-means-clustered insertion and deletion, with no real timestamps. A caching bug in the recall code first reported first-snapshot recall instead of the runbook average, and fixing it reversed the ranking. Because only the average is reported, nothing in the track can split recall by item age or arrival batch. The per-checkpoint ground truth that would be needed to do so does exist in the repo.

### Cited Findings
- **Results paper**: "Results of the Big ANN: NeurIPS'23 competition", arXiv 2409.17424, v1 submitted 25 Sep 2024 (preprint) — [arXiv](https://arxiv.org/abs/2409.17424). It was later published (PR) in **NeurIPS 2025 (Advances in NeurIPS 38), Datasets and Benchmarks Track** — [NeurIPS proceedings](https://papers.nips.cc/paper_files/paper/2025/hash/63092d79154adebd7305dfd498cbff70-Abstract-Datasets_and_Benchmarks_Track.html). The four tracks were sparse, filtered, out-of-distribution and streaming.
- **Workload**: the index starts empty and runs a "runbook" of insert, delete and search steps in "roughly 4:4:1 ratio". The data is "generated by clustering the original dataset with k-means and packing points in the same cluster into contiguous indices", and insertions go "one cluster at a time". `max_pts` caps the number of active points — [neurips23 README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/README.md).
- **Final runbook structure (per the results paper)**: 64 k-means clusters and 5 rounds of 4×64 = 256 steps each, so 1,280 batches. Each step inserts points from one cluster, searches with all queries, deletes a fraction of that cluster's points, and searches again — [arXiv HTML 2409.17424v1](https://arxiv.org/html/2409.17424v1).
- **Dataset size conflict**: the repo README says "The final run will use `msturing-30M-clustered`, a 30M slice of the MSTuring dataset", and the preliminary runs used `msturing-10M-clustered` with `delete_runbook.yaml` — [neurips23 README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/README.md). The results paper's HTML describes a "10M slice of MS Turing" — [arXiv HTML](https://arxiv.org/html/2409.17424v1). The final-run size should be checked against `final_runbook.yaml` before it is cited.
- **Limits**: 1 hour for the whole runbook and 8 GB DRAM, on an Azure D8lds_v5 (8 vCPU, 16 GB) — [neurips23 README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/README.md); [arXiv HTML](https://arxiv.org/html/2409.17424v1).
- **How recall is computed**: "the recall is computed against the set P consisting of all insertions, minus deletions, at the point at which the query was issued", and "we averaged the recall of queries at various checkpoints over runs that complete in an execution window" — [arXiv PDF 2409.17424](https://arxiv.org/pdf/2409.17424). The README says "Entries will be ranked by average recall over queries at all check points", and that the streaming track "reports a single recall number per runbook/algorithm", with no QPS/recall curve. Ground truth per checkpoint can be downloaded (`download_gt`) or computed (`compute_gt.py`) — [neurips23 README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/README.md). The paper's HTML also has a sentence saying runs are "ranked by maximum recall across searches", which contradicts the averaging rule. That is an internal inconsistency in the paper text — [arXiv HTML](https://arxiv.org/html/2409.17424v1).
- **Recall bug**: the organizers "discovered that recall had been calculated incorrectly due to a caching error". The wrong numbers were recall at the first snapshot, not the average over the runbook. After the fix and rerun, the declared winner changed (Puck to PyANNS) — [arXiv HTML](https://arxiv.org/html/2409.17424v1). The paper's table (via the HTML):

| Entry | Recall, pre-fix | Recall, corrected |
|---|---|---|
| Puck (originally declared winner) | 0.985 | 0.0921 |
| hwtl_sdu_anns_stream | 0.9674 | 0.7693 |
| PyANNS (corrected winner) | 0.9597 | 0.8865 |
| DiskANN (baseline) | 0.883 | 0.7218 |
| cufe | 0.8189 | 0.6481 |

- **Baselines in the README**: DiskANN scores 0.924 recall@10 on msturing-10M-clustered/delete_runbook (23 min) and 0.883 on msturing-30M-clustered/final_runbook (45 min) — [neurips23 README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/README.md). The 0.883 matches DiskANN's pre-fix number in the table above.
- **Winning techniques**: PyANNS is the DiskANN graph with 8-bit scalar quantization, which allows deeper graph search within the time limit. Puck (Baidu) is a four-level hierarchical cluster index: VQ at the top two levels, PQ at the bottom two, deletions via a flag array, and insertions by extending the build algorithm — [arXiv HTML](https://arxiv.org/html/2409.17424v1).
- **Post-competition leaderboard** (volunteer-maintained, update dated 1 March 2024): "The leading entry had a recall of 0.99786", ranked on recall@10 with the 1-hour runbook limit. The results file is `res_final_runbook_AzureD8lds_v5.csv` — [ongoing leaderboard](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/ongoing_leaderboard/leaderboard.md). Vendor claims: Pinecone reports 0.9975 — [Pinecone blog](https://www.pinecone.io/blog/pinecone-algorithms-set-new-records-for-bigann). Zilliz reports 0.9982, "surpassing the track winner and the Pinecone solution with recalls of 0.986 and 0.9975" — [Zilliz blog](https://zilliz.com/blog/zilliz-vector-search-algorithm-dominates-BigANN). These are self-reported, and the "0.986 track winner" matches the pre-fix Puck figure, not the corrected one.
- **Other runbooks in the repo**: (a) clustered (`random-xs-clustered`, `msturing-10M-clustered`), inserted in clustered order; (b) `delete_runbook.yaml`, clustered inserts then "deletes a fraction of each cluster"; (c) **wikipedia-35M**, which "inserts each point with a randomly chosen expiration time: never, in 100 steps, or in 20 steps" (a wikipedia-1M variant also exists); (d) msturing-10M **sliding window**, which "inserts half the points, then maintains the index at a consistent size using a sliding window"; (e) **replace** runbooks (clustered and random), where "`replace` provides a range of existing tags and a range of vector ids" and points are replaced with ids from the same cluster or a different random one; (f) the final runbook, msturing-30M-clustered with "several rounds of insertion and deletion in clustered order" — [neurips23 streaming README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/streaming/README.md).
- **Limitations the paper acknowledges**: the index handles one operation class at a time, "a simplification" compared with real concurrent systems. The baseline's lazy deletions lower recall until consolidation — [arXiv HTML](https://arxiv.org/html/2409.17424v1). The paper does not discuss per-query or tail recall — same source.
- **Follow-up tracks**: I found no 2024–2026 Big-ANN competition or new streaming track. The newest Big-ANN output is the NeurIPS 2025 D&B publication of the 2023 results — [NeurIPS proceedings](https://papers.nips.cc/paper_files/paper/2025/hash/63092d79154adebd7305dfd498cbff70-Abstract-Datasets_and_Benchmarks_Track.html). The README says the leaderboard "is no longer attached to a competition and maintained on a purely volunteer basis" — [neurips23 README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/README.md). **CANDOR-Bench** (SIGMOD 2026, DOI 10.1145/3786630) is built on Big-ANN-Benchmarks and argues that the streaming track lacks open-world features such as event-rate control, drift and fault/noise injection (see Q4).

### Inferences
- The track's statistic is the mean over queries and checkpoints of |retrieved ∩ GT_t|/10, where GT_t is the live set at time t. An index that systematically misses recently inserted items would be detected only to the extent that those items are among queries' true top-10 at a checkpoint. In clustered order the newest cluster can dominate some queries' neighbourhoods, so part of the effect would show up. It would still be averaged together with all other checkpoints and queries into one number, and nothing attributes misses to item age.
- The bug shows that a single runbook-level average can hide a dramatic change over time: Puck went from 0.985 at the first snapshot to 0.09 averaged. That is strong precedent for reporting a recall **trajectory** and its decomposition, not one scalar.
- The per-checkpoint GT files plus each point's insertion step from the runbook are enough to compute per-age recall after the fact. The data exists. The metric does not.

### Gaps
- I could not read `final_runbook.yaml` directly (the runbooks README path returned 404), so the 10M vs 30M discrepancy and the exact per-step delete fractions are unresolved.
- I did not confirm which algorithm holds the 0.99786 leaderboard entry.
- I could not confirm whether queries are fixed across checkpoints or drawn from the current cluster. The README implies one fixed query set ("search with all queries").

## Q2. VIBE (Vector Index Benchmark for Embeddings): streaming, OOD, metrics

### Takeaway
VIBE covers OOD queries but **no streaming, update, insert or delete workloads**. It reports average recall against QPS, plus a recall breakdown for the hardest and easiest queries by relative contrast. It has no per-item metric, and streaming is not listed as a limitation either.

### Cited Findings
- Title "VIBE: Vector Index Benchmark for Embeddings", arXiv 2505.17810. v1 is dated 23 May 2025, v2 4 Aug 2026 and v3 23 Aug 2026. The arXiv comments field says "Journal of Data-centric Machine Learning Research (2026)" — [arXiv abs](https://arxiv.org/abs/2505.17810). The v3 HTML itself names no venue, so treat it as likely DMLR 2026 (PR) without independent confirmation — [arXiv HTML v3](https://arxiv.org/html/2505.17810v3).
- Scope: 22 open-source index implementations on 11 in-distribution and 8 OOD datasets. OOD means "queries and the corpus are drawn from different distributions", and includes multimodal and MIPS (approximate attention, multi-vector reduction) sets — [arXiv abs](https://arxiv.org/abs/2505.17810); [GitHub](https://github.com/vector-index-bench/vibe).
- Metrics: average recall (per-query recall averaged over test queries) and QPS. Each configuration runs 5 times and the minimum time is kept. Recall is also broken down by query difficulty using relative contrast RC100, with the "100 hardest and 100 easiest" queries reported separately. Significance tests use paired per-query latencies. The default k is 100, and everything runs on a single core — [arXiv HTML v3](https://arxiv.org/html/2505.17810v3); [GitHub](https://github.com/vector-index-bench/vibe).
- No streaming, insert or delete evaluation. The limitations section (6.2) does not mention it and says "we focus on million-scale datasets". The related work names Big-ANN's streaming task but VIBE does not evaluate it — [arXiv HTML v3](https://arxiv.org/html/2505.17810v3).
- ANN-Benchmarks now says it "is no longer actively maintained" and points users to VIBE. Its latest results are "as of April 2025", on static pre-split train/test datasets with no updates — [ann-benchmarks GitHub](https://github.com/erikbern/ann-benchmarks).

### Inferences
- VIBE's per-query hardness slice (RC100) is the closest any mainstream static benchmark comes to looking past average recall. It stratifies **queries**, not **indexed items**, and it assumes a build-once index, so it cannot detect an insertion-age effect.

### Gaps
- I did not read the final ~28% of the v3 HTML (appendices). I cannot rule out a per-query recall distribution plot in the appendix.

## Q3. Industry and vendor benchmarks: Intel SVS, Cosmos DB DiskANN, VectorDBBench, Qdrant, Weaviate, ANN-Benchmarks

### Takeaway
Every vendor streaming benchmark I found reports **average recall@k per step, plotted over time**. Insertion order is random or k-means clustered, never real timestamps. None splits recall by item age, insertion batch, or reachability of individual items. Qdrant's and Weaviate's public benchmarks are static.

### Cited Findings
- **Intel SVS "Benchmarks for Dynamic Indexing"**: starts with a random 70% sample. Each iteration deletes 1% of indexed vectors and adds 1% of unindexed vectors, both "chosen at random". Consolidation runs every 5 iterations. The metric is k-recall@k with k=10, plotted over iterations. Datasets are deep-96-100M, open-images-512-13M/1M and rqa-768-10M/1M, compared against FreshVamana and HNSWlib. Claims: SVS keeps recall stable, HNSWlib's recall degrades because it lacks consolidation, up to 9.4x QPS (1M) and 4.6x (>10M) at 0.9 recall, and 3.6x/17.7x faster addition/consolidation. The page gives no number of iterations — [Intel SVS docs](https://intel.github.io/ScalableVectorSearch/benchs/dynamic.html). These are vendor claims.
- **Azure Cosmos DB with DiskANN Part 4: Stable Vector Search Recall with Streaming Data** (Microsoft blog, 7 May 2025). It uses Big-ANN-style runbooks: (a) expiration runbooks where each step "inserted a 1/T_max fraction of the dataset in random order", with lifespans of 100/50/10 steps in a 1:2:10 ratio (MSTuring 1M, Wiki-Cohere 10M); (b) a clustered runbook with 64 k-means clusters and 5 rounds, inserting and then deleting a random share per cluster. Labels conflict between 1M and 10M. After each step it runs a fixed set of 5–10k queries against that step's GT. For the clustered runbook "we measured the average query recall after processing each cluster". The comparison baseline "handles delete operations by just dropping the vector". The post says clustered is harder than expiration but gives no numbers in the text — [Cosmos DB blog](https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-with-diskann-part-4-stable-vector-search-recall-with-streaming-data/).
- **VectorDBBench / VDBBench 1.0 (Zilliz)**: has a streaming case that runs searches while inserts continue at a fixed rate. Sources name it differently ("Insertion-Under-Load", `StreamingPerformanceCase`). The dashboard shows how recall fluctuates during ingestion, e.g. Cohere 10M at 500 rows/s — [Zilliz VDBBench 1.0 blog](https://zilliz.com/blog/vdbbench-1-0-benchmarking-with-your-real-world-production-workloads); [VectorDBBench GitHub](https://github.com/zilliztech/VectorDBBench). An OceanBase vendor post (June 2026, per search snippet; the fetch was rate-limited) used `StreamingPerformanceCase` and noted recall "measured at 80% write progress (theoretical max recall for this case is 0.80)" — [OceanBase blog](https://en.oceanbase.com/blog/streaming-workload-benchmark-5-vector-databases-compared). This **suggests VectorDBBench's streaming recall is computed against full-dataset ground truth, not the live set**, which mixes "not yet inserted" with "inserted but missed". Unverified, because I could not read the case source.
- **Qdrant benchmarks**: the flow uploads data, "waits for all required indexes to be constructed, and then performs searches". It reports RPS, mean and p95 latency, and index time, with precision used only as a threshold. Single-node results are "Updated: January/June 2024". There is no streaming or per-query recall — [Qdrant benchmarks](https://qdrant.tech/benchmarks/).
- **Weaviate ANN benchmark**: Recall@10/@100 against dataset GT, QPS, mean and P99 latency over 10,000 requests, and import time, on a fixed dataset. There is no streaming and no per-query recall distribution. No date is given — [Weaviate docs](https://docs.weaviate.io/weaviate/benchmarks/ann).
- **ANN-Benchmarks**: unmaintained, results as of April 2025, static only — [GitHub](https://github.com/erikbern/ann-benchmarks).
- **ByteDance UBASE** (arXiv 2608.30607): reports a 30-hour streaming test on Cohere data at a fixed insert rate with concurrent queries (from a search snippet, not read in full) — [arXiv](https://arxiv.org/pdf/2608.30607).

### Inferences
- Vendor streaming tests ask whether average recall stays flat over time, which is a question about index-wide degradation. An index whose old items stay well connected while each new batch is under-linked could keep a flat average if new items are a small share of each query's true top-k. That is exactly the setting where an age effect goes unseen.
- If VectorDBBench's streaming ground truth is the full dataset, its recall cannot tell apart missing-because-not-inserted from missing-because-unreachable. It could not detect an age effect even in principle.

### Gaps
- I did not find VectorDBBench's streaming case source, so its recall definition is unconfirmed.
- I found no Milvus, pgvector-official, LanceDB or Elastic streaming benchmark with per-item metrics. I did not search exhaustively.

## Q4. Academic streaming and dynamic ANN benchmarks and surveys (2021–2026)

### Takeaway
Academic streaming benchmarks (CANDY, CANDOR-Bench, the deletion-evaluation framework) and dynamic-index papers (FreshDiskANN, Quake, CleANN, MERIT, Yi, DGAI, streaming quantization) all report **average recall per step or window, over time**. The one exception is the HNSW "unreachable points" paper (arXiv 2407.07871). It counts in-degree-zero points and uses the whole dataset as K=1 queries, which is a per-item self-retrievability test. I found no dedicated survey of dynamic ANN benchmarking. "SIEVE" is a filtered-search system, not a streaming benchmark.

### Cited Findings
- **CANDY: A Benchmark for Continuous Approximate Nearest Neighbor Search with Dynamic Data Ingestion**, arXiv 2406.19651, v1 dated 28 Jun 2024 only (preprint, cs.DB). The abstract says "Traditional benchmarks primarily assess retrieval effectiveness in static contexts and often overlook update efficiency" and finds that "simpler AKNN baselines often surpass more complex alternatives in terms of recall and latency". It highlights distribution shift and micro-batching effects. Code is at github.com/intellistream/candy — [arXiv](https://arxiv.org/abs/2406.19651). The abstract does not say how recall is aggregated.
- **CANDOR-Bench** (SIGMOD 2026, Experiments & Analysis track, DOI 10.1145/3786630; PR). It targets in-memory continuous ANNS under "dynamic open-world streams" and is built on Big-ANN-Benchmarks. It adds high-frequency ingestion, drift modelling including modality shift, noise injection, and concurrent query/update execution. Over 12 datasets and 19 algorithms, "no single algorithm consistently delivers high recall, throughput, and update efficiency". Author PDF: [author site](https://shuhaozhangtony.github.io/contents/research_papers/2026/2026_candor_bench_sigmod_2026.pdf). The details come from search snippets; I could not render the PDF or reach the ACM page (403). The relationship to CANDY, which shares an author, is unconfirmed.
- **How Should We Evaluate Data Deletion in Graph-Based ANN Indexes?**, arXiv 2512.06200, 5 Dec 2025, accepted at the NeurIPS 2025 Workshop on ML for Systems (workshop PR). Metrics: 1-Recall@10 after each update step, QPS-search/add/delete, and memory per step. The workload is repeated insert/delete cycles that delete consecutive IDs, on n=5×10^5 indexes over SIFT1M, GIST1M, DEEP1M, GloVe-100 and a SIFT1B subset. It reports that logical deletion's accuracy deteriorates with repeated updates and proposes "Deletion Control". It has **no reachability or per-item metrics** — [arXiv abs](https://arxiv.org/abs/2512.06200); [HTML](https://arxiv.org/html/2512.06200).
- **Enhancing HNSW Index for Real-Time Updates: Addressing Unreachable Points and Performance Degradation**, arXiv 2407.07871, v2 dated 15 Jul 2024 (preprint; a CEUR-WS Vol-4250 PDF also appears in search results, venue unconfirmed). An unreachable point is "a point that possesses outgoing edges but lacks incoming edges in all layers". Under replaced-update (HNSW-RU), unreachable points grow to about 3–4% (GIST, SIFT after ~3,000 iterations of 5% delete+reinsert) and 2–3% (ImageNet, after 200 iterations). On SIFT recall falls about 3% and this "cannot be mitigated by adjusting HNSW searching parameters". The Gist/ImageNet evaluation **uses the full dataset as queries with K=1**. The workloads are Full_Coverage, Random, and New_Data (SIFT2M sliding from the first million to the second). The paper proposes MN-RU with a backup index — [arXiv HTML v2](https://arxiv.org/html/2407.07871v2); [CEUR-WS](https://ceur-ws.org/Vol-4250/paper776.pdf).
- **FreshDiskANN: A Fast and Accurate Graph-Based ANN Index for Streaming Similarity Search**, arXiv 2105.09613, 20 May 2021 (the arXiv page lists no venue). It claims ">95% 5-recall@5" with thousands of concurrent inserts, deletes and searches per second — [arXiv](https://arxiv.org/abs/2105.09613).
- **Quake: Adaptive Indexing for Vector Search**, OSDI 2025 (PR; [USENIX PDF](https://www.usenix.org/system/files/osdi25-mohoney.pdf)); arXiv 2506.03437. Its Wikipedia-12M workload is a **real temporal trace** "derived from monthly Wikipedia page additions and page-view" statistics, April 2013 to December 2021. It "simulates monthly inserts of new pages, followed by 100,000 search queries sampling page embeddings with probability proportional to their page views". The other workloads are OpenImages-13M (inserts/deletes by class label) and synthetic MSTuring (RO, and IH growing from 1M to 10M). Recall is per-query recall@k averaged and tuned to 90%, plotted over time ("near 90%"), with no per-item or per-age split — [arXiv HTML v2](https://arxiv.org/html/2506.03437v2).
- **Quantization for Vector Search under Streaming Updates**, arXiv 2512.18335, 20 Dec 2025 (preprint; Amazon/UC Berkeley). It clusters the data, starts from a subset of clusters and inserts the rest. A freshness parameter α controls whether queries come from the newest cluster (α=1) or uniformly from all clusters seen (α=0). It says "there are few options for benchmark datasets with an intrinsic notion of streaming order and a relevant level of drift". It reports recall-10@10 against vectors streamed, as a fraction of a RebuildPQ reference with a rolling median and 10th–90th quantile band. Data: 100M-scale Deep1B, BigANN and Text2Image. It has **query-side freshness only, no per-item-age recall** — [arXiv HTML](https://arxiv.org/html/2512.18335).
- **CleANN: Efficient Full Dynamism in Graph-based Approximate Nearest Neighbor Search**, arXiv 2507.19802, v1 26 Jul 2025 and v2 26 Jul 2026. A related DOI (10.1145/3816782.3819219) suggests an ACM publication, unconfirmed. It claims query quality "at least as good as if the index had been built statically" under fully dynamic concurrent workloads, with 7–1200x throughput gains. The abstract mentions no per-item metric — [arXiv](https://arxiv.org/abs/2507.19802).
- **Efficient and Effective In-place Graph-based Vector Index Updates** (system "Yi"), arXiv 2607.15576, 17 Jul 2026 (preprint). Claims on an 800M dataset: 1.75x update throughput, 1.8x concurrent search throughput, 73% of peak memory. The abstract gives no per-item or age metrics — [arXiv](https://arxiv.org/abs/2607.15576).
- **MERIT: Efficient In-Place Deletion for Dynamic Graph-Based Approximate Nearest Neighbor Indexes**, arXiv 2607.29173 (preprint). It claims deletion at about the cost of one insertion and stable recall as deletions accumulate (from a search snippet) — [arXiv](https://arxiv.org/html/2607.29173).
- **DGAI: Decoupled On-Disk Graph-Based ANN Index for Efficient Updates and Queries**, arXiv 2510.25401 (preprint). It reports 8.17x faster inserts and 8.16x faster deletes than FreshDiskANN/OdinANN (from a search snippet) — [arXiv](https://arxiv.org/html/2510.25401).
- **Building An Integrated Vector Database System in PostgreSQL**, arXiv 2608.15994 (preprint, PDF metadata 2026-08-18). Per a search snippet, it follows the Big-ANN runbook method and reports that "pgvector's recall declines over successive delete-insert cycles", which it attributes to connectivity loss in in-place HNSW updates. I could not read the PDF text — [arXiv](https://arxiv.org/pdf/2608.15994).
- **Updatable Balanced Index for Stable Streaming Similarity Search** (IEEE BigData 2025 per the PDF filename; not read) — [PDF](https://sheng.whu.edu.cn/papers/25bigdata.pdf).
- Static context: **Graph-Based Vector Search: An Experimental Evaluation of the State-of-the-Art**, SIGMOD 2025, is a static benchmark (seen only as a citation in search results).
- **VecDBLens: An Evaluatology-Based Framework for Vector Database Diagnosis**, arXiv 2611.15105, 11 Nov 2026 (preprint). It uses ANOVA-based attribution and aggregate recall, and does not mention streaming — [arXiv](https://arxiv.org/abs/2611.15105).
- **SIEVE**: in my knowledge this is a filtered-vector-search system ("collection of indexes"), not a streaming benchmark. I did not verify it in this session.

### Inferences
- The field's common design is a runbook plus average recall per step, with the trajectory plotted. "Stability" means a flat average. Only 2407.07871 measures anything per item (in-degree zero, and every point queried for itself at K=1). It is a graph-topology diagnostic under replace-updates, not a benchmark metric, and it does not split by insertion time.
- Several systems (CleANN, MERIT, SVS, the Cosmos DB DiskANN post) claim recall "as good as static" or "stable". Under the field's metrics none of these claims tests whether recently inserted items are as retrievable as old ones.

### Gaps
- I found no paper titled as a "survey" of dynamic/streaming ANN, or an "updatable vector index benchmark", from 2024–2026. Absence is not proven.
- CANDOR-Bench's metric definitions (per-window? cumulative?) are unverified because the PDF was not rendered.
- I did not check whether CANDY or CANDOR-Bench report per-batch recall restricted to the newest batch.

## Q5. Per-query recall metrics (tail, fraction below threshold, PQR-Search) and per-item metrics (retrievability, coverage, unreachable fraction)

### Takeaway
Per-query metrics are emerging. PQR-Search (Nov 2026) reports the fraction of queries below a recall threshold and shows it worsening after updates, VIBE slices by query hardness, Steiner-hardness measures per-query effort, and a hubness study (SIGMOD 2026) explains greedy-search failure on anti-hubs. **Per-item metrics are nearly absent from ANN benchmarking.** The concepts exist elsewhere: IR "retrievability" (Azzopardi and colleagues), hubness and anti-hubs, unreachable or in-degree-zero points, and an early-stage "dark matter" exposure-audit tool. **I found no benchmark that reports recall by item age or insertion batch.**

### Cited Findings
- **Per-Query Recall Guarantees for Approximate Nearest Neighbor Search in Dynamic Vector Databases** (PQR-Search), arXiv 2611.07579. v1 is dated 5 Nov 2026 and v2 11 Nov 2026, described as an "Extended version of a paper submitted to ICDE 2027" (preprint, under review) — [arXiv abs](https://arxiv.org/abs/2611.07579).
  - Its guarantee: Pr[Recall(q) < τ] ≤ δ per query, and E[Recall(q)] ≥ τ, over a random rotation inside the index. It works by pruning 1-bit codes of rotated IVF residuals with exact error quantiles — [arXiv abs](https://arxiv.org/abs/2611.07579).
  - Its evidence: with indexes tuned to 0.99 average recall, "5.0–19.2% of the queries had recall below 0.99" (k=100, in-distribution). On OOD queries "8.1–95.8% of queries fell even below recall 0.9", and the abstract says up to 99.6% are below target. "4.8% of the queries had recall 0 on DiskANN with an average Recall@10 of 0.9". A top-5-tag aggregate changed for up to 27% of queries — [arXiv HTML v2](https://arxiv.org/html/2611.07579v2); [arXiv abs](https://arxiv.org/abs/2611.07579).
  - Its update experiment: on yandex at 0.99 average recall, "five consecutive steps, each inserting 10% of the data arriving in cluster order and deleting the oldest 10%". FreshDiskANN's below-threshold fraction went "from 13.8% to 20.0%" (k=100, τ=0.99). On the NeurIPS'23 streaming runbook, the failure rate "stayed at most δ in all 33 search steps without retuning" — [arXiv HTML v2](https://arxiv.org/html/2611.07579v2). **Conflict**: a search snippet attributed "18.5% of its queries fell below recall 0.99" to FreshDiskANN, possibly from v1, while v2 says 13.8%→20.0%. Cite v2.
  - It does **not** split recall by new vs old items or measure per-item reachability. Its related work says dynamic-index work (FreshDiskANN, Quake, partition maintenance) was "evaluated by average recall", and that "per-query conditional guarantees cannot be obtained by conformal methods" (ConANN, CTR) — [arXiv HTML v2](https://arxiv.org/html/2611.07579v2).
- **Steiner-Hardness: A Query Hardness Measure for Graph-Based ANN Indexes**, PVLDB 17(13):4668–4682, 2024, doi:10.14778/3704965.3704974 (PR). ### Inferences
- **No benchmark I found could detect "HNSW drops relevant new items 2–3x as often as old ones."** Average recall (Big-ANN, SVS, Cosmos DB, VectorDBBench, Quake, CANDY/CANDOR, the deletion framework) and per-query recall (PQR-Search, VIBE RC100) both stratify by **query**. An age effect lives in the **(query, true neighbour)** pairs, grouped by the neighbour's insertion time. The closest precedents are 2407.07871's dataset-as-queries K=1 self-retrieval test and IR retrievability.
- What a fair benchmark of age-invariant retrievability would need, as design requirements drawn from the gaps above:
  1. Per-checkpoint live-set ground truth, as Big-ANN already has, **plus each item's insertion step**.
  2. A per-neighbour miss rate, P(true neighbour missed | neighbour age bucket), reported as a ratio (new/old) with confidence intervals. It should be computed over pairs, not queries, so the effect is not diluted.
  3. Query sets that put new items in the true top-k in comparable numbers. Otherwise queries concentrated on old regions hide the effect. A freshness-controlled query mix like 2512.18335's α, or self-queries, would do this.
  4. Insertion orders that include random, k-means clustered (Big-ANN) and **real temporal order** (Quake's Wikipedia trace is the only real-timestamp trace found), so that age is not confounded with region.
  5. Insert-only growth as well as churn, so that the effect is not just deletion damage.
  6. A static-rebuild control with the same item set, so that age-attributable misses are measured relative to a from-scratch index. The point of the control is to separate "hard region" from "arrived late".
  7. Matched ef or recall operating points, and per-item self-retrievability (K=1) or unreachable fraction as diagnostics.
  8. Both average and tail reporting, given the Big-ANN bug's lesson that one scalar can hide large changes over time.

## Q6. Insertion-order designs and real timestamps

### Takeaway
Insertion orders in use are random (SVS, expiration runbooks), k-means clustered (Big-ANN final and clustered runbooks, Cosmos DB, PQR-Search, 2512.18335), class-label ordered (Quake OpenImages), consecutive-ID deletion (2512.06200), and random expiration lifetimes (wikipedia-35M). **The only benchmark workload with real timestamps I found is Quake's Wikipedia-12M trace** (monthly page additions 2013–2021, page-view-weighted queries). Authors explicitly note how few datasets have an intrinsic streaming order.

### Cited Findings
- Big-ANN: k-means clusters packed into contiguous IDs and inserted one cluster at a time. wikipedia-35M uses random expirations (never, 100 or 20 steps). There are also sliding-window and replace runbooks — [neurips23 README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/README.md); [streaming README](https://github.com/harsha-simhadri/big-ann-benchmarks/blob/main/neurips23/streaming/README.md).
- Cosmos DB: random-order expiration runbooks and a 64-cluster, 5-round clustered runbook — [Cosmos DB blog](https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-with-diskann-part-4-stable-vector-search-recall-with-streaming-data/).
- Intel SVS: random 1% delete and 1% add per iteration from a random 70% start — [SVS docs](https://intel.github.io/ScalableVectorSearch/benchs/dynamic.html).
- Quake: real Wikipedia monthly-addition trace (Apr 2013 to Dec 2021) with page-view-proportional queries. OpenImages ordered by class. Synthetic MSTuring with spatial skew — [Quake arXiv HTML](https://arxiv.org/html/2506.03437v2); [OSDI'25 PDF](https://www.usenix.org/system/files/osdi25-mohoney.pdf).
- 2512.18335: cluster-ordered drift, with the quote "few options for benchmark datasets with an intrinsic notion of streaming order and a relevant level of drift" — [arXiv HTML](https://arxiv.org/html/2512.18335).
- PQR-Search: "inserting 10% of the data arriving in cluster order and deleting the oldest 10%" (FIFO by age) — [arXiv HTML v2](https://arxiv.org/html/2611.07579v2).
- 2407.07871 New_Data: SIFT2M sliding window from the first million to the second million — [arXiv HTML v2](https://arxiv.org/html/2407.07871v2).
- A GitHub harness generates synthetic timestamped vectors with tunable temporal density and time-vector correlation, but its ANN backend is pending — [GitHub](https://github.com/sumik1999/Filtered_ANN_Index). An open GitHub issue in a third-party project proposes a drift runbook with oldest-first deletes. It is a proposal only — [GitHub issue](https://github.com/samyama-ai/samyama-graph/issues/1986).
- Related temporal-IR context: "Still Fresh? Evaluating Temporal Drift in Retrieval Benchmarks", arXiv 2603.04532, about corpus drift invalidating retrieval benchmarks — [arXiv](https://arxiv.org/pdf/2603.04532). "Time-Decayed Vector Search in the Rhythm of TANGO", arXiv 2609.00548, about joint semantic and temporal-freshness ranking, not index-age bias — [arXiv](https://arxiv.org/pdf/2609.00548).
- An early practitioner argument for streaming benchmarks: "Please Use Streaming Workload to Benchmark Vector Databases" (Medium / Towards Data Science). Per the search snippet, it proposes separate data and query streams and tracking recall per query. It could not be fetched (403), and its date is unverified — [Medium](https://ekzhu.medium.com/please-use-streaming-workload-to-benchmark-vector-databases-bb0154480263).

### Inferences
- Clustered order deliberately ties age to region: the newest items are a contiguous region. An age effect measured under clustered order can therefore be confounded with region hardness. Random order removes the confound but is unrealistic, and real timestamps such as Quake's Wikipedia trace are realistic but rare. A fair benchmark should run all three and report the age effect under each.
- None of these designs is analysed per item age, even where age is explicit (PQR-Search's FIFO deletes, wikipedia-35M expirations, Quake's monthly trace).
